## コンテキスト

カラーパレットジェネレーターの核となる色空間の選定が必要。パレット生成時に明度を均等に分布させつつ、知覚的に自然なカラースケールを生成するには、従来の HSL/HSB では知覚的均一性が不十分であり、専門的な色空間の採用が求められた。

## 検討した選択肢

### 選択肢 A: OKLCH（Oklab ベースの円筒座標系）

- 概要: Björn Ottosson が提案した Oklab 色空間の円筒座標表現。知覚的均一性に優れる
- 使用ライブラリ / API: 自前実装（sRGB ↔ Linear RGB ↔ XYZ D65 ↔ Oklab ↔ OKLCH の変換チェーン）
- 外部依存: 依存なし
- メリット: 知覚的に均一な明度スケールが得られる、CSS Color Level 4 で `oklch()` が標準化、色相の回転が直感的
- デメリット: 変換が多段階で計算コストがやや高い、sRGB ガマット外の色が生成されるためガマットマッピングが必要
- ブラウザ対応: 変換は JavaScript で行うため全ブラウザ対応

### 選択肢 B: HSL（CSS 標準の色相・彩度・明度）

- 概要: CSS で広く使われる色空間
- 使用ライブラリ / API: ネイティブ CSS / 簡易な数式
- 外部依存: 依存なし
- メリット: 実装が簡単、CSS ネイティブサポート
- デメリット: 知覚的均一性が低く、同じ明度でも色相によって見た目の明るさが異なる
- ブラウザ対応: 全ブラウザ対応

### 選択肢 C: CIELAB / CIELCh

- 概要: 従来の知覚均一色空間
- 使用ライブラリ / API: 自前実装 or ライブラリ（chroma.js 等）
- 外部依存: ライブラリ使用時は npm 依存あり
- メリット: 長年の実績、知覚均一性がある程度確保
- デメリット: 青色域で色相シフトが発生する問題、OKLCH に比べて均一性が劣る
- ブラウザ対応: JavaScript 変換のため全ブラウザ対応

## 決定

**選択肢 A: OKLCH** を採用。知覚的均一性が最も高く、カラーパレット生成において自然な明度グラデーションが得られる。CSS Color Level 4 での標準化により将来性もある。変換ロジックは外部依存なしで `color-utils.js` に自前実装し、バンドルサイズへの影響を最小化した。

## 技術的詳細

### 実装方針

`color-utils.js` に変換チェーンをすべて実装。パレット生成時はベースカラーの Chroma（C）と Hue（h）を保持し、Lightness（L）のみを変動させることで色相を維持した明度スケールを生成する。sRGB ガマット外の色は二分探索によるガマットマッピング（Chroma 削減）で処理する。

### 使用する主要 API / ライブラリ

```
- Math.cbrt, Math.atan2, Math.pow（OKLCH 変換の行列演算・三角関数）
- 自前実装: hexToOklch, oklchToHex, gamutMapOklch 等
```

### マイグレーション戦略

初回実装のため該当なし。

## 影響範囲

- `js/color-utils.js`: 変換ロジック全体
- `js/state.js`: パレット生成・更新時の OKLCH 計算呼び出し
- `js/ui.js`: OKLCH 値の表示
- `js/chart.js`: 明度チャートの描画

## パフォーマンス考慮

- 変換チェーンは 5 段階（sRGB → Linear → XYZ → Oklab → OKLCH）で計算量は中程度
- ガマットマッピングの二分探索は最大約 14 回のイテレーション（精度 0.0001）
- 20 色パレットでも瞬時に完了するレベルでパフォーマンス問題なし

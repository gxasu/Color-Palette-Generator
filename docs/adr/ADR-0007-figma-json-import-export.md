## コンテキスト

生成したカラーパレットをデザインツール（Figma）で利用したいというニーズがある。パレットデータの外部共有・バックアップ手段も必要であり、デザイナーとの連携を考慮したデータ形式の選定が求められた。

## 検討した選択肢

### 選択肢 A: Figma Variables JSON 形式

- 概要: Figma の Variables 機能と互換性のある JSON 構造（コレクション / モード / 変数）
- 使用ライブラリ / API: なし（自前でシリアライズ/デシリアライズ）
- 外部依存: 依存なし
- メリット: Figma との直接連携が可能、モード（ライト/ダーク）の概念が一致、デザイナーとのワークフローに統合しやすい
- デメリット: Figma 固有のフォーマット、他のデザインツールとの互換性がない
- ブラウザ対応: ファイルダウンロード/アップロードなので全ブラウザ対応

### 選択肢 B: Design Tokens Format（W3C DTCG）

- 概要: W3C Design Tokens Community Group が策定中の標準フォーマット
- 使用ライブラリ / API: なし or Style Dictionary
- 外部依存: Style Dictionary 使用時は npm 依存
- メリット: 標準化が進行中、ツール非依存
- デメリット: 仕様が未確定、Figma への直接インポートには変換が必要
- ブラウザ対応: 全ブラウザ対応

### 選択肢 C: CSS カスタムプロパティとして出力

- 概要: `--color-name-100: #xxx;` の形式で CSS ファイルを出力
- 使用ライブラリ / API: なし
- 外部依存: 依存なし
- メリット: 開発者がそのままコピペで使える
- デメリット: 再インポートが困難、モード情報の表現が不自然
- ブラウザ対応: 全ブラウザ対応

## 決定

**選択肢 A: Figma Variables JSON 形式** を採用。本ツールの主要ユースケースが「パレットを生成して Figma で使う」であるため、Figma との親和性を最優先とした。コレクション名 / モード / 変数名（`パレット名/ステップ`）の階層構造が、アプリ内部のデータモデル（パレット → モード → カラー配列）と自然に対応する。

## 技術的詳細

### 実装方針

`import-export.js` に集約:
- **エクスポート**: 全パレットを 1 つのコレクションとして出力。各パレットのカラーは `パレット名/ステップ番号` の変数名で、モードごとに RGBA 値を格納
- **インポート**: JSON をパースし、変数名の `/` 区切りでパレット名を推定。各モードのカラー値から OKLCH 値を逆算してアプリ内部のデータ構造に変換
- **ダウンロード**: Blob + `URL.createObjectURL` でブラウザからダウンロード

### 使用する主要 API / ライブラリ

```
- JSON.stringify / JSON.parse
- Blob API
- URL.createObjectURL / revokeObjectURL
- FileReader API（インポート時）
```

### マイグレーション戦略

該当なし（初回設計時に採用）。

## パフォーマンス考慮

- JSON シリアライズ/デシリアライズは小規模データのため瞬時に完了
- Blob 生成とダウンロードはユーザー操作起点で発火するため UI ブロックの懸念なし

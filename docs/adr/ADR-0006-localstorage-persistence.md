## コンテキスト

ユーザーが作成したパレットデータをブラウザセッションをまたいで保持する必要がある。バックエンドサーバーを持たない静的 Web アプリケーションのため、クライアントサイドでの永続化手段が求められた。

## 検討した選択肢

### 選択肢 A: localStorage

- 概要: Web Storage API の同期的なキー・バリューストア
- 使用ライブラリ / API: `localStorage.setItem / getItem`
- 外部依存: 依存なし
- メリット: 実装が極めてシンプル、同期 API で扱いやすい、全ブラウザ対応
- デメリット: 容量制限（約 5MB）、同期 API のため大量データで UI ブロックの可能性、文字列のみ保存可能
- ブラウザ対応: 全ブラウザ対応

### 選択肢 B: IndexedDB

- 概要: ブラウザ内蔵の非同期オブジェクトデータベース
- 使用ライブラリ / API: `indexedDB` / idb（ラッパーライブラリ）
- 外部依存: ラッパー使用時は npm 依存あり
- メリット: 大容量対応、構造化データの保存、非同期 API
- デメリット: API が複雑、小規模データには過剰
- ブラウザ対応: 全モダンブラウザ

### 選択肢 C: File System Access API

- 概要: ユーザーのファイルシステムに直接保存
- 使用ライブラリ / API: `showSaveFilePicker / showOpenFilePicker`
- 外部依存: 依存なし
- メリット: ユーザーが保存先を制御できる、データのポータビリティ
- デメリット: ユーザー操作が毎回必要、ブラウザサポートが限定的（Chromium 系のみ）
- ブラウザ対応: Chromium 系のみ

## 決定

**選択肢 A: localStorage** を採用。パレットデータは JSON シリアライズしても数十 KB 程度で容量制限に達する可能性は低く、同期 API のシンプルさが開発効率に寄与する。データのインポート/エクスポート機能（ADR-0007）を別途用意し、バックアップ・移行手段を確保する。

## 技術的詳細

### 実装方針

- 保存キー: `color-palette-generator`
- 保存タイミング: `notify()` のたびに自動保存（状態変更ごと）
- 読み込み: アプリ起動時に `loadFromLocalStorage()` で復元
- エラーハンドリング: `try/catch` で静かに失敗（プライベートブラウジング等での localStorage 無効に対応）

### 使用する主要 API / ライブラリ

```
- localStorage.setItem / getItem
- JSON.stringify / JSON.parse
```

### マイグレーション戦略

該当なし（初回設計時に採用）。将来のスキーマ変更時はバージョン番号の付与を検討する。

## 影響範囲

- `js/state.js`: `saveToLocalStorage()` / `loadFromLocalStorage()` 関数

## パフォーマンス考慮

- `JSON.stringify` は状態変更のたびに実行されるが、データ量が小さいため影響は無視できる
- パレット数が極端に多い場合（数百件）はデバウンスの導入を検討

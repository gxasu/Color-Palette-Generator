## コンテキスト

フレームワークなしのバニラ JavaScript（ADR-0004）を採用したため、アプリケーション状態の管理パターンを自前で設計する必要がある。パレットの追加・削除・編集、テーマ切り替え、モード管理等の状態変更を UI に反映する仕組みが求められた。

## 検討した選択肢

### 選択肢 A: 自作 Pub-Sub + イミュータブル状態更新

- 概要: `subscribe()` でリスナーを登録し、状態変更時に全リスナーに通知する。状態オブジェクトはスプレッド構文で毎回新しいオブジェクトを生成
- 使用ライブラリ / API: なし（自前実装）
- 外部依存: 依存なし
- メリット: シンプル、外部依存ゼロ、デバッグが容易
- デメリット: 状態変更のたびに全体が再レンダリングされる、大規模化には不向き
- ブラウザ対応: 全ブラウザ対応

### 選択肢 B: Redux（スタンドアロン）

- 概要: 予測可能な状態管理ライブラリ
- 使用ライブラリ / API: `redux` or `@reduxjs/toolkit`
- 外部依存: npm パッケージ
- メリット: DevTools 対応、ミドルウェア、堅牢な設計パターン
- デメリット: アクション/リデューサーのボイラープレート、小規模アプリには過剰
- ブラウザ対応: 全ブラウザ対応

### 選択肢 C: Proxy ベースのリアクティブ状態

- 概要: `Proxy` を使って状態変更を自動検知
- 使用ライブラリ / API: JavaScript Proxy API
- 外部依存: 依存なし
- メリット: 変更検知が自動、コードが簡潔
- デメリット: デバッグが困難、Proxy の落とし穴（ネストされたオブジェクト、配列操作等）
- ブラウザ対応: 全モダンブラウザ

## 決定

**選択肢 A: 自作 Pub-Sub + イミュータブル状態更新** を採用。アプリケーション規模が小さく、状態変更のパターンが限定的（パレット CRUD、テーマ切り替え等）であるため、シンプルな実装で十分。状態変更時に `notify()` で全リスナーに通知し、`render()` で全パネルを再描画する設計とした。

## 技術的詳細

### 実装方針

`state.js` に集約:
- `state` オブジェクト: パレット配列、選択中パレット ID、テーマ、コレクション名等
- `getState()`: 現在の状態を取得
- `subscribe(listener)`: リスナー登録（解除関数を返す）
- `notify()`: 全リスナーに通知 + LocalStorage 保存
- 各 mutation 関数（`createPalette`, `updatePaletteBaseColor` 等）: スプレッド構文でイミュータブルに状態を更新し `notify()` を呼ぶ

### 使用する主要 API / ライブラリ

```
- Array.prototype.map / filter（イミュータブルな配列操作）
- スプレッド構文（オブジェクトの浅いコピー）
- localStorage（notify 時に自動保存）
```

### マイグレーション戦略

該当なし（初回設計時に採用）。

## アーキテクチャ適合性

- [x] ES Modules によるモジュール分割を遵守
- [x] 状態管理（state.js）の pub-sub パターンを遵守
- [x] Vite ビルドパイプラインとの整合性
- [x] Material Web コンポーネントとの共存
- [x] LocalStorage 永続化との互換性
- [x] 既存の CSS カスタムプロパティ（MD3 トークン）体系との整合

## 影響範囲

- `js/state.js`: 状態管理ロジック全体
- `js/ui.js`: `subscribe(render)` で状態変更を購読
- `js/app.js`: 初期化時に `loadFromLocalStorage()` と `initUI()` を呼び出し

## パフォーマンス考慮

- 状態変更のたびに全 3 パネルを再レンダリング（`innerHTML` で DOM を再構築）
- 現在のアプリ規模（パレット数十件程度）では十分高速
- 大量のパレット（数百件）を扱う場合は差分レンダリングの検討が必要
